Sobel kernel, from scalar to SIMD

Part 2 of Canny on the Xeon Silver 4208. Go step by step; every step has a picture or animation.

1. The scalar loop: one pixel at a time

The loop visits pixels left to right, top to bottom. For each pixel it reads the 3×3 window around it, multiplies by the Sobel weights, and writes two outputs: mag (how strong the edge is) and angle (which way it points). Press play.

2. What one pixel needs (the "independent operation")

The slides call one output with its chain of dependent instructions an independent operation. Every pixel is one; no pixel needs another pixel's result. Here is the chain for one pixel, after our two cleanups (no clamps inside the image, and the 4 direction bins instead of atan2):

StepInstructionsKind of unit
read 8 neighbours8 loadsload unit
gx = (tr−tl) + (br−bl) + 2(mr−ml)3 sub, 1 add, 1 fmaFP unit

So the kinds of unit this kernel needs: FP unit (add/sub/mul/fma/compare), divider (sqrt), logic unit (and/or/xor/blend), load unit, store unit.

3. What the Xeon has (and how many)

Each core has execution ports; a port is one functional unit that can start one new instruction every cycle (pipelined). The counts below are Cascade Lake values from uops.info / Agner Fog; your assignment-1 throughput benchmark is how you confirm them (throughput 2/cycle ⇒ 2 units).

Key point: add, sub, mul, fma and compare all share the same 2 FP units (ports 0 and 1). The divider sits behind port 0. Latency of an FP instruction is 4 cycles.

4. SIMD: 8 pixels per instruction

One AVX2 register holds 8 floats, so one instruction does the same step for 8 neighbouring pixels (a "group"). Instead of reading neighbours one by one, we load 8 at a time, shifted by one column. Press play to watch group A's loads.

After the 8 loads, gx = (tr−tl)+(br−bl)+2(mr−ml) is 5 instructions for 8 pixels, not 5 per pixel. Each lane (column) of the registers is one pixel.

5. The whole image: how the kernel sweeps the matrix

Zoom out to the whole image (here 66 columns × 8 rows; the real L1 test is 258 × 8). Each iteration computes 32 pixels of one row = groups A, B, C, D. It reads the 3 rows around that row (dashed box). Then it moves 32 columns right; at the end of the row it drops one row down. The outer ring (grey) has no full 3×3 window, so the scalar code does it.

group A / C group B / D border · scalar code rows read this iteration

Notice the overlap: row y is read as the "middle" row now, as the "top" row for row y+1 and as the "bottom" row for row y−1. Every input pixel is read 3 times, which is why it must stay in cache (L1) — the memory-layout part of the report.

7. Peak: which unit is the bottleneck?

Count the instructions for one group (8 pixels) per kind of unit, divide by how many of those units exist. That's how many cycles each unit needs. The largest one is the bottleneck, and that is the peak (best possible) speed — same method as assignment 2: units × 1 per cycle.

Peak = 9 cycles per 8 pixels ≈ 1.13 cycles/pixel (0.89 pixels per cycle). Bottleneck: the 2 FP units. (Your current kernel uses more adds and blends: 25 cycles per 16 pixels ≈ 1.56 cycles/pixel.)

8. Peak throughput, counted from the assembly

Throughput = work finished per cycle. The 2 FP units can start at most 2 instructions per cycle (lecture: units × 1 per cycle, pipelined) — that is the machine's instruction throughput. If one iteration needs X instructions on those units and makes P pixels, the kernel's peak throughput is 2 × P ÷ X pixels per cycle. Multiply by the clock for pixels per second, and by FLOP per pixel for GFLOP/s. Fewer FP instructions per pixel ⇒ higher peak throughput.

9. Chains and kernel size: how many groups at once?

A chain is a sequence of instructions where each one needs the result of the previous one, so it cannot start until that result is ready (FP result = 4 cycles later). Instructions in different chains don't wait for each other, so they can run at the same time. Below is one group drawn as a dependency graph: each box sits at the cycle it can start at the earliest; an arrow means "needs that result". The longest path (orange) is the critical path.

Read it like this: in cycles 0–3 there are 6 subtracts that don't depend on each other — plenty for 2 units. But after that the graph gets narrow: one add, then one fma, then one mul... each waiting 4 cycles. One group needs about 32 cycles from start to finish, while the 2 FP units could do its 18 FP instructions in 9. During those waits the units sit idle — unless other groups (independent chains) fill the gaps.

Simulation: the 2 FP units with G groups in flight

This schedules the real graph above, cycle by cycle (FP latency 4, logic 1, blend 2, sqrt 12 with one every 6 cycles) for 256 pixels = 32 groups. G = how many groups are in flight at once: a new group may start only when the group G places before it has finished — that is what a kernel of G groups, software-pipelined (or the CPU's out-of-order engine), gives you. Each cell is one FP-unit slot; the letter is the group; amber = a logic op borrowing an FP port.

One group leaves the units idle while it waits on its 33-cycle chain; each extra group fills those gaps. Rule of thumb from this: groups in flight ≈ critical path ÷ cycles one group needs at peak = 33 ÷ 9 ≈ 4. So the kernel keeps 4 groups = 32 pixels in flight. (The simulator's scheduling is simple, so it levels off at 1.30 rather than the 1.13 peak; the trend is what matters.)

10. Check it fits: registers and L1 cache

Registers: no spilling

AVX2 has 16 ymm registers. A spill is when the compiler runs out and parks a value on the stack (a store + later load). Plan so we never exceed 16 at any moment:

StageWhat is liveRegisters
A. gx, gy for all 4 groups (interleaved A,B,C,D)gx and gy accumulators × 4 groups = 8, plus ~1 temporary per group in flight = 412
B. finish group A (mag, sqrt, bin, 2 stores)gx, gy of B, C, D = 6 held; group A working set (gx, gy, sum, |gx|, |gy|, product, mask) ≈ 612
C, D, E. finish B, then C, then Dfewer held each time≤ 12
Constants (2.0, tan22.5, sign mask, 45/90/135)kept in memory and used as memory operands, e.g. vmulps ymm, ymm, [tan22] — they come from L1 via the load units, which have spare cycles (4 of 9)0

Max ≈ 12 of 16 → no spill, with a few spare. Two coding rules make it work: use t + t instead of multiplying by a 2.0 constant (or let the fma read 2.0 from memory), and write group A's finishing code before group B's so the compiler doesn't keep everything alive at once. The CPU still overlaps the groups at run time because it renames registers internally (the Architecture slides: "logical registers vs physical registers" — 16 names, ~180 real registers).

How to check you didn't spill — no ymm stores/loads to the stack in the kernel loop:

objdump -d --no-show-raw-insn build/CMakeFiles/sobel_kernel.dir/src/sobel_kernel.cpp.o | awk '/sobel_row/,/ret/' | grep -E 'ymm.*\(%rsp\)|\(%rsp\).*ymm' | wc -l

It should print 0. Build with -O3 -mavx2 -mfma (16 registers) so the result also holds on any AVX2 machine.

L1 cache (32 KB) for the peak test

blur + mag + angle = 12 bytes per pixel. Keep ≤ 24 KB ⇒ ~2,048 pixels.

Use a wide, short image: 258 × 8 floats ≈ 24.2 KB, so each row gets 8 iterations of 32 pixels.

Summary: FP units are the bottleneck → peak 1.13 cycles/pixel → one group's chain is 33 cycles, so ~4 groups must be in flight → 32 pixels per iteration → fits in 16 registers with no spill (max ~12) and the data fits in L1 → then measure on the Xeon and compare to the peak.
